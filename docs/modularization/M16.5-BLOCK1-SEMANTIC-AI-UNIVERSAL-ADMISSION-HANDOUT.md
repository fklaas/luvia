## User outcome

Luvia interprets a whole request before choosing an owner. A sentence about
switching trips cannot become a Places search merely because it contains a
generic verb. When meaning is not reliable enough, Luvia asks one short
question. It does not guess.

For restaurants, activities, culture, sights, attractions and events, the same
Booking Owner provides a compact statement such as `Reservierung möglich`,
`Ticket erforderlich`, `Tickets verfügbar` or `Eintritt noch ungeklärt` and the
next safe action. The notice is consumed by AI Chat, Places and Journey/Timeline
suggestions; consumers do not invent booking policy.

## Owner and provider architecture

`booking.admission.v1` is a browserless component of the existing Booking Core.
It is exposed only through additive reads on `booking.v1`.

Provider layers:

| Layer | Providers / route | Current Integration state | What remains |
|---|---|---|---|
| Direct official | official ticket/reservation URL | immediately usable when present | public E2E with a real Place |
| Verified public contact | public booking email plus source URL and verified/public flags | immediately usable after owner evidence | public preview/send/receipt test; never infer raw email |
| Transaction API | Tiqets, Viator | capability + registry + partner-gated adapters | commercial/API access, secret authorization, Edge transport, live health and provider E2E |
| Activity handoff/partner discovery | GetYourGuide, FareHarbor, Bókun, Regiondo, bookingkit, Xola, Checkfront | capability + domain detection | provider-by-provider contract and activation decision |
| Event ticket handoff | EVENTIM, Reservix, Ticketmaster | capability + domain detection | verified event product and public handoff E2E |
| Dining compatibility | TheFork, OpenTable, Zenchef, Quandoo, Resy, SevenRooms, Tock and existing fallbacks | retained | existing provider-specific activation/evidence continues |

The provider claims above follow the official product boundaries, not feature
name similarity:

- Tiqets Distributor API documents catalogue, live availability/pricing,
  creation, confirmation, cancellation, order/ticket retrieval and webhooks;
  test and production access require a partner agreement and separate keys:
  <https://developers.tiqets.dev/>.
- Viator distinguishes affiliate handoff from merchant/commerce access. The
  local adapter therefore stays `partner_required` and does not borrow
  supplier-side amendment operations for the partner API:
  <https://docs.viator.com/partner-api/>.
- Ticketmaster Discovery exposes event discovery and purchase URLs. Direct
  reserve/purchase/order capability belongs to separate partner access and is
  not claimed by the Discovery adapter:
  <https://developer.ticketmaster.com/products-and-docs/apis/discovery-api/v2/>.

`partner_required` and `discovery` are deliberately not `connected`. An adapter
rejects before network access while partner activation is absent.

## Truth rules

- Category makes admission relevant but never proves that payment, a ticket or
  a reservation is required.
- `reservable=true` proves support only.
- A URL proves that a handoff exists only.
- Required/recommended/free/timed-entry labels require explicit provider or
  official-place evidence.
- Email fallback requires a valid address, public+verified flags and a source
  URL. A raw Place email is excluded.
- Opening a route is not a purchase, reservation or message.

## Additive hotel decision lane — 2026-09-02

Hotels are now specified as an independent Planning and Booking product. Luvia
does not produce one card per portal and does not claim an impossible search of
every market source. The Booking Owner instead accepts normalized offers from
a small set of broad, approved supplier layers, deduplicates the same property
and compares provider prices only for equivalent stay/rate products.

The first compact result contains exactly three explainable choices: cheapest
complete comparable total, best flexible option and best personal fit. Required
taxes/fees, dates, party/rooms, currency, room/board/bed signature, freshness,
cancellation/payment conditions and provider reliability are explicit.
Commission is not a ranking input.

The local owner adapter now exposes `booking.v1.reads.compareStayOffers` over
the browserless `booking.stay-decision.v1` core. No live price is claimed until
an approved provider responds. Activation priority, owner application pack and
the KAYAK/Expedia/Booking/Hostelworld supply strategy are documented in
`M16.5-AFFILIATE-ACTIVATION-AND-HOTEL-DECISION-PLAN.md`.
