Status: **owner-first decomposition complete; `.125` implementation tranche is locally implemented and under Step-17/18 acceptance**
Plan position: stable Redesign/Recovery Step **16 of 18**

## 1. Non-negotiable ownership model

This backlog extends the existing owner graph. It does not create a second
Intelligence owner and it does not let a composition surface acquire Domain
Truth.

| Truth or operation | Sole owner boundary | Intelligence may do | Intelligence may never do |
|---|---|---|---|
| Place, venue, coordinates and place lifecycle | `places.v1` | rank source-backed projections, explain uncertainty, propose a Places command | fabricate a venue or write Places state |
| Booking/provider availability and reservation lifecycle | `booking.v1` | explain provider evidence and prepare an owner command | claim availability/success without provider evidence |
| Day Graph, open windows, ordering and temporal conflicts | `journey.v1` | simulate and propose a revised Day Graph | silently reorder or copy Journey truth |
| Trip lifecycle and active Trip | `trip.v1` | read the active Trip and propose a Trip command | switch or mutate a Trip directly |
| Identity, consent and explicit preferences | `identity.v1` | use purpose-bound projections and propose small explained preference changes | infer sensitive traits or persist raw context |
| Device location | `LocationPort` behind an explicit on-device context grant | consume coarse, expiring context for one allowed purpose | request, persist or transmit precise GPS implicitly |
| Memory narrative lifecycle | `memory.v1` | propose a source-backed Event-to-Memory thread | copy Media or write a Memory silently |
| Group membership, invitations and roles | reserved `collaboration.membership.v1` | read only an honest foundation projection | productize membership mutations before M18.1 |
| Cross-owner event envelopes | `events.v1` | publish causal envelopes after an owner result exists | treat the event log as canonical Domain Truth |
| Reasoning, evidence graph, planning trace and action ledger | existing `intelligence.v1` and `intelligence.actions.v1` | compile, orchestrate, explain and record receipts | execute foreign store/DB writes |

Every mutation path is invariant:

`Preview → explicit confirmation → public Owner Command → Owner Receipt → Recovery → explicit Undo/compensation`

There is no confirmation bypass, hidden retry, optimistic provider success,
synthetic event, consumer-side mutation or dark Legacy replacement.

## 2. Shared contract envelopes

All Step-16 slices use these envelopes before feature-specific fields.

### 2.1 Owner-backed input envelope

Required fields:

- `requestId`, `tripId`, `actorProjectionId`, `locale`, `timeZone`;
- `purpose` and the exact owner contract requested;
- `observations[]` with `owner`, `ownerEntityId`, `sourceId`, `observedAt`,
  `freshUntil`, `sourceClass` and `verificationStatus`;
- optional purpose-bound coarse context from `LocationPort`;
- no raw GPS, authentication secret, payment data or unbounded chat transcript.

### 2.2 Derived proposal envelope

Required fields:

- `proposalId`, `compilerMessageHash`, `traceId`, `createdAt`, `expiresAt`;
- `ownerReads[]`, `ownerCommandProposals[]`, `dependencies[]`;
- `assumptions[]`, `conflicts[]`, `missingInputs[]`, `staleEvidenceIds[]`;
- a human-readable explanation tied to reason and evidence IDs;
- `automaticMutation: false` and `rawMessageStored: false`.

### 2.3 Command and receipt envelope

Required fields:

- `confirmationId`, `confirmedBy`, `confirmedAt`, `previewDigest`;
- one public owner command, idempotency key and owner capability version;
- result `status` from the owner, never inferred by the composer;
- `receiptId`, `correlationId`, `causationId`, timestamps and redacted payload
  digest;
- `recoveryMode`: `retry-safe`, `reconcile-owner`, `compensating-command` or
  `manual-provider-recovery`;
- optional inverse owner command, which itself requires a new Preview and
  explicit confirmation.

### 2.4 Global freshness classes

| Class | Meaning | Product behaviour |
|---|---|---|
| `live` | observed inside the provider/owner SLA | may support a preview until `freshUntil` |
| `recent` | still useful but outside live SLA | visible warning; refresh before external mutation |
| `stale` | expired or owner marks superseded | may explain history; cannot support a mutation |
| `unknown` | timestamp/source missing | cannot be presented as verified current truth |
| `conflicted` | sources or owners disagree | block mutation and show the exact disagreement |

Offline caches retain the original `observedAt`, `freshUntil` and provenance.
Reconnection never rewrites an old observation as fresh.

## 4. USP slices

### 4.1 Route-Uncertainty Simulation — S16.03

Owner-first contract:

- Inputs: Journey segment IDs, Places coordinates from `places.v1`, transport
  observations with source and freshness, time window and accessibility
  constraints.
- Output: a derived distribution (`p50`, `p80`, `p95` arrival), assumptions,
  missing inputs and affected Journey entry IDs. It is a simulation, not route
  truth.
- Freshness: traffic/transit observations must remain live; static geometry may
  be recent when its source version is unchanged.
- Privacy: coarse origin is the default; exact device position requires an
  explicit, expiring route-planning grant and is never persisted by Intelligence.
- Failures: missing coordinates, stale network evidence, contradictory modes,
  offline provider and impossible time window yield a visible partial/blocked
  result.
- Mutation/receipt: simulation is read-only. “Apply buffer” creates a Journey
  Preview and follows the global command/receipt/undo invariant.
- Evals: deterministic percentiles; stale traffic cannot appear live; DST and
  timezone boundaries; inaccessible route; offline cache; no coordinate
  fabrication; no silent Journey reorder.
- Rollback: disable `routeUncertainty`; Journey and Places remain unchanged.

### 4.2 Live Disruption Recovery — S16.05

- Inputs: an owner-originated Booking/Places/Journey disruption envelope,
  affected Day Graph, verified current alternatives and user constraints.
- Output: ranked recovery proposals with losses, gains, cancellation risk,
  source age and a causal planning trace.
- Freshness: external alternatives must be refreshed immediately before a
  Booking command; cached alternatives are explanation-only.
- Privacy: provider references are redacted in consumer receipts; no payment or
  booking secret enters Intelligence.
- Failures: unknown provider outcome blocks blind retry and offers owner
  reconciliation; no alternative becomes an honest “keep current plan” result.
- Receipts: one receipt per owner command, correlated by a recovery session ID;
  partial success is never collapsed into a global success.
- Evals: cancellation race, venue closure, offline interruption, reconnect,
  duplicate provider response, partial Journey compensation and rollback.
- Rollback: disable recovery composer; retain owner receipts and current plan.

### 4.3 Explainable Planning Trace — S16.01

- Inputs: compiled intents, owner observations, decision candidates and reason
  codes.
- Output: immutable evidence nodes and decision edges, with missing/stale
  evidence listed explicitly.
- Freshness: trace preserves the observation timestamps from owners.
- Privacy: message hash replaces raw prompt; exact location and private raw
  context are excluded.
- Failures: missing evidence makes a decision unverified, not silently valid.
- Receipts: trace ID and digest are attached to Preview and final receipt.
- Evals: stable digest, causal edge completeness, source removal, unknown
  freshness, conflicting owner facts and redaction.
- Rollback: hide the explanation projection; owner commands/receipts remain.

### 4.4 Causal Feedback Learning — S16.06

- Inputs: explicit feedback, confirmed outcome, bounded features, evidence IDs.
- Output: small proposed preference deltas, capped per event, owned by Identity.
- Freshness: outcome must refer to a current, confirmed owner result.
- Privacy: sensitive/inferred attributes are excluded; no passive surveillance,
  hidden embeddings or raw conversation persistence.
- Failures: ambiguous outcome, inferred-only feedback or missing evidence is
  rejected.
- Mutation/receipt: Identity Preview and explicit confirmation precede the
  `identity.v1` command; inverse delta is the compensation.
- Evals: cap enforcement, repeated feedback, contradictory feedback, rejection
  without explicit input, Identity command failure and exact undo.
- Rollback: disable learner; accepted Identity history is not rewritten.

### 4.5 On-Device Context Gate — S16.02

- Inputs: allowed purpose, explicit grant, precision, expiry and device context.
- Output: the minimum context for one request, or a reason-coded denial.
- Freshness: expired grants and old sensor observations are denied.
- Privacy: process on-device; default coarse; `persist:false`; purpose cannot be
  widened downstream.
- Failures: permission denied, sensor unavailable, revoked grant, background
  request and unsupported purpose yield no coordinates.
- Receipt: privacy-safe grant decision receipt containing purpose/precision and
  expiry, never coordinates.
- Evals: deny-by-default, coarse rounding, precise opt-in, expiry, revocation,
  offline use and background/resume.
- Rollback: disable context consumption and fall back to explicit place input.

### 4.6 Offline-First CRDT Reiseplan — S16.07 (reserved)

- Sole truth owner: Journey. Intelligence is not the CRDT owner.
- Inputs: Journey-signed operation IDs, actor membership capability, vector or
  hybrid logical clock, base graph version and redacted owner references.
- Output: deterministic merged Day Graph projection, unresolved semantic
  conflicts and sync receipts.
- Freshness: local operations remain `pending-sync`; only the Journey owner can
  mark them reconciled.
- Privacy: per-Trip encrypted scope; no cross-Trip replication; removed members
  cannot receive new operations.
- Failures: revoked membership, causal gap, incompatible schema, duplicate op,
  clock skew and tombstone conflict.
- Mutation/receipt: every local edit already has an explicit Journey command
  receipt; sync adds reconciliation status, never retroactive silent success.
- Evals: two-/three-device convergence, remove-vs-edit, reorder-vs-delete,
  duplicate/reordered delivery, cold restart, offline week, membership revoke,
  schema migration and rollback replay.
- Rollback: turn off CRDT adapter, keep operation log export, restore read-only
  server projection. Productization is blocked until Journey and Collaboration
  authorization contracts are active.

### 4.7 Destination Digital Twin — S16.08

- Inputs: verified Places/Booking/Journey/weather/event observations and a Trip
  time window.
- Output: expiring derived destination-state graph with provenance on every
  node; never a copied Domain Truth store.
- Freshness: node-specific TTL; query result exposes mixed freshness instead of
  one global “live” badge.
- Privacy: Trip-scoped; no exact traveler location; no external sharing without
  an explicit purpose and owner command.
- Failures: sparse coverage, source conflict and stale nodes remain visible.
- Receipts: read receipt contains projection version and evidence digest; any
  downstream mutation uses its own owner receipt.
- Evals: provenance completeness, TTL expiry, source withdrawal, timezone/DST,
  Trip isolation, offline partial twin and no synthetic nodes.
- Rollback: drop/rebuild the derived cache; owners are untouched.

### 4.8 Day Rehearsal Engine — S16.04

- Inputs: a Journey Day Graph, uncertainty distributions, open/closed owner
  projections and explicit user constraints.
- Output: scenario comparison (best/expected/worst), breakpoints, recovery
  options and planning trace.
- Freshness: rehearsal timestamp and every external evidence age are visible.
- Privacy: device context only through S16.02; no raw GPS storage.
- Failures: incomplete Day Graph, stale provider evidence and circular
  dependency produce a partial rehearsal, never a confident score.
- Mutation/receipt: rehearsal is read-only; choosing a scenario creates one or
  more separately confirmed owner commands with separate receipts.
- Evals: no mutation during simulation, deterministic seeded scenarios,
  impossible itinerary, accessibility, children/group constraints, offline and
  mid-confirmation evidence expiry.
- Rollback: disable rehearsal UI/core; original Journey projection remains.

## 5. Verified Event Intelligence Core — S16.09–S16.12

### 5.1 Boundary and truth model

Reserved public projection: `intelligence.verified-events.v1`.

The core owns only evidence-backed event claim normalization, verification
state, temporal/spatial edges, confidence explanations and planning traces.
It does not own Place, Booking, Journey, Memory, Identity, Collaboration or
provider truth. `events.v1` remains cross-owner envelope transport and is not
used as a canonical event database.

No event is product-visible unless the minimum evidence gate passes:

- stable `eventClaimId` and source-native identifier;
- source URL or provider reference, source class and retrieval receipt;
- title from the source (never model-created), start/end with IANA timezone;
- source-backed venue identity or an explicitly “venue pending” state;
- `observedAt`, `freshUntil`, verification state and change fingerprint;
- cancellation/status evidence when advertised as live;
- no coordinates generated from venue text: coordinates must come from Places
  or a source observation and retain provenance.

`verified` means the current claim is supported by an official organiser,
venue or contracted provider observation inside its freshness SLA. Corroborated
independent sources may increase confidence, but never repair missing primary
identity/time provenance. Claims failing the gate are `candidate-hidden` or
`unverified-hidden`, not event cards.

### 5.2 Event input/output contract

Inputs:

- source observations (`official`, `venue`, `provider`, `partner`) with terms,
  retrieval and freshness metadata;
- Places venue projection, Journey time windows, Booking capability/status,
  optional weather observations, Identity preference projection and optional
  Collaboration group projection;
- never scraped or model-invented facts without an authorized source gateway.

Outputs:

- `VerifiedEventClaim` with immutable evidence links and field-level provenance;
- `EventChangeSet` for time, venue, cancellation and source drift;
- `SpatioTemporalEventGraph` as an expiring derived projection;
- `EventFitProposal` and explanation, with no owner mutation;
- owner command proposals for Journey, Places, Booking or Memory only after the
  user chooses an event.

Freshness defaults, configurable only by a source-specific policy:

- cancellation/live schedule: refresh on view and before action; never cache as
  current beyond 15 minutes;
- ticket/booking availability: provider live check before Preview and again if
  Preview expires;
- start/end/venue: 6-hour maximum for same-day events, 24 hours otherwise;
- cultural context: source/version bound; visible citation and retrieved date;
- weather: observation/forecast owner SLA, shown on every substitution.

### 5.3 Dynamic Map-Time Brushing

- Owners: Places for geometry/venue, Journey for time windows; Event core only
  joins derived projections.
- UX: synchronized horizontal timeline plus a modern live map. Brushing a time
  range filters pins; panning/zooming filters the visible extent without
  rewriting either owner.
- Pins: color encodes source-backed event category, while shape/status encodes
  verification and drift. Color alone is never the only signal.
- Interaction: fluid pointer/touch pan, wheel/pinch zoom, keyboard pin traversal,
  hover/focus Floating detail and Escape close. Reduced Motion removes flight
  and interpolation while retaining state change.
- Failures: map tiles unavailable → accessible list/timeline; source expired →
  pin hidden or visibly stale; no geocoded provenance → no map pin.
- Evals: range boundary/DST, clusters, zoom/pan/hover/focus, 320/360/390 widths,
  high density, empty range, offline tiles, reduced motion and no invented pin.
- Rollback: disable `eventMapTimeBrush`; retain verified list projection.

### 5.4 Event-to-Memory Thread

- Inputs: a verified EventClaim ID, confirmed attendance/visit evidence and
  user-selected Media IDs.
- Output: Memory Preview referencing the event and source; no copied Media.
- Privacy: no attendance inference from GPS or photos; explicit selection only.
- Failure: event cancellation or missing visit evidence is explained and does
  not auto-create a memory.
- Receipt/undo: `memory.v1` command receipt and explicit inverse archive/remove
  command where the owner supports it.
- Evals: no attendance inference, deleted Media, source withdrawal, Memory
  failure, exact undo and Trip isolation.
- Rollback: disable event thread composer; existing Memory owner objects remain.

### 5.5 Cultural Context Layer

- Inputs: verified event identity plus attributable museum, venue, municipal or
  editorial source documents authorized for use.
- Output: concise context with field/claim citations, locale and uncertainty.
- Privacy: no traveler traits are sent to a source; personalization happens on
  bounded projections.
- Failure: no trustworthy citation → context unavailable, never generated as
  fact; source disagreement is shown.
- Receipt: read trace with source/version IDs, not copied copyrighted text.
- Evals: citation entailment, source removal, multilingual names, conflicting
  histories, unsupported claim refusal and copyright-length guard.
- Rollback: hide context; event claim remains.

### 5.6 Serendipity Window

- Inputs: Journey-owned open window, nearby verified events, route uncertainty
  and explicit constraints.
- Output: optional ranked proposals with fit explanation and a “keep free” choice.
- Privacy: coarse location unless a separate explicit grant exists.
- Failure: no verified event or insufficient travel buffer produces no proposal.
- Mutation: selecting an event produces a Journey Preview; booking remains a
  separate Booking Preview.
- Evals: tight buffer, accessibility, family/group constraints, stale event,
  offline, decline/no learning and separate confirmations.
- Rollback: disable serendipity; open window remains untouched.

### 5.7 Group Taste Divergence

- Status: read-only foundation until `collaboration.membership.v1` is active.
- Inputs: consented, member-scoped preference projections and explicit choices;
  absent members are “unknown”, never assigned inferred tastes.
- Output: divergence explanation, common-ground candidates and minority-impact
  warning.
- Privacy: no individual preference disclosure beyond authorized group scope.
- Failure: missing membership capability blocks; sparse preferences remain
  unknown.
- Receipt: read trace only. Voting/invite writes remain blocked for M18.1.
- Evals: minority protection, equal scores, private preference, revoked member,
  no inferred trait and attempted unauthorized vote.
- Rollback: hide divergence projection.

### 5.8 Weather-Safe Event Substitution

- Inputs: owner weather observation/forecast, verified event status, indoor/
  outdoor source evidence, Journey graph and Booking cancellation policy.
- Output: alternatives with weather and switching costs; never a silent swap.
- Freshness: refresh weather and event availability before confirmation.
- Failure: uncertain weather or unknown venue suitability remains explicit;
  “weather-safe” cannot be claimed without source evidence.
- Receipts: separate Booking cancellation/new command and Journey replacement
  receipts; partial failure remains partial.
- Evals: forecast changes during Preview, cancellation fee, no alternative,
  offline, unknown indoor status and compensation failure.
- Rollback: disable substitution composer; no owner data changes.

### 5.9 Cancellation & Venue Drift Detection

- Inputs: successive source observations and owner venue projection.
- Output: field-level `EventChangeSet` with old/new source fingerprints and
  affected Journey/Booking references.
- Freshness: same-day claims are refreshed on open and before action.
- Privacy: no user data is needed for claim detection; impact joins happen
  Trip-locally.
- Failure: source outage is `unknown`, not cancellation; ambiguous venue rename
  is a review state.
- Receipt: detection envelope plus each subsequent owner-command receipt.
- Evals: cancellation, postponement, venue rename, coordinate drift, source
  outage, duplicate event and false-positive guard.
- Rollback: disable detector; keep last verified projection with visible age.

### 5.10 Live Schedule Reconciliation

- Inputs: verified provider schedule, current Journey projection and correlated
  Booking status.
- Output: reconciliation diff with additions/removals/time shifts and conflicts.
- Freshness: live schedule is refreshed before applying any diff.
- Failure: provider disagreement or unknown Booking outcome blocks automatic
  reconciliation.
- Mutation/receipt: user confirms a Journey command Preview; every Booking
  consequence is a separate owner command.
- Evals: simultaneous shifts, DST, duplicate session, partial provider result,
  reload during confirmation, reconnect and exact Journey compensation.
- Rollback: disable live reconciliation; prior Journey owner state remains.

### 5.11 Spatio-Temporal Event Graph

- Inputs: only VerifiedEventClaims and Places/Journey projections with evidence.
- Output: expiring graph nodes/edges (`sameVenue`, `overlaps`, `reachableWithin`,
  `fitsWindow`, `sourceRevisionOf`) and reasoned queries.
- Freshness: every edge inherits the minimum freshness of its evidence inputs.
- Privacy: graph contains no traveler exact-location history and is Trip-scoped
  when joined to Journey.
- Failure: missing coordinates/time means the respective edge is absent, never
  guessed.
- Receipt: read trace with graph version and source digest.
- Evals: temporal boundaries, coordinate provenance, graph expiry, source
  withdrawal, cross-Trip isolation, deterministic rebuild and zero synthetic
  nodes.
- Rollback: drop/rebuild derived graph from owner/source observations.

## 6. Shared Event Core failure vocabulary

| Code | Meaning | Required visible response |
|---|---|---|
| `source-unverified` | no accepted primary evidence | hide claim; never show as event |
| `freshness-expired` | evidence is outside SLA | show age if historical; refresh before action |
| `source-conflict` | two trusted observations disagree | show conflict and block mutation |
| `venue-unresolved` | no provenance-backed Place/venue identity | list-only pending state; no map pin |
| `provider-unavailable` | source gateway failed | honest unavailable/offline state |
| `provider-outcome-unknown` | external mutation outcome cannot be proven | reconcile with Booking owner; no blind retry |
| `permission-denied` | purpose/capability not granted | remove private context and offer manual input |
| `owner-foundation-only` | required owner is not productized | block command and identify milestone |
| `partial-owner-success` | one of several commands failed | show per-owner receipts and recovery choices |

## 7. Acceptance eval packs

No slice may leave `planned` state without all applicable packs:

1. **Source truth:** zero source-less events/pins; field-level provenance;
   cancellation/source-outage distinction; freshness expiry.
2. **Owner boundaries:** static dependency test; no foreign store/DB writes;
   public commands only; receipts identify the owner.
3. **Mutation protocol:** Preview digest, explicit confirmation, owner command,
   success/failure/unknown receipts, recovery and separately confirmed undo.
4. **Privacy:** deny-by-default GPS, coarse/precise grants, expiry/revoke, Trip
   isolation, no raw prompt/location persistence and group-scope enforcement.
5. **Offline/reconnect:** cold offline, warm cache, stale labels, queued owner
   operation state, reconciliation and duplicate response.
6. **Temporal:** locale/timezone/DST, overnight event, postponement, overlapping
   windows and mixed freshness.
7. **Interaction:** desktop/mobile/touch/keyboard/reload/back, 320/360/390,
   zoom/pan/hover/focus/Floating, reduced motion and accessible non-map fallback.
8. **Recovery:** provider timeout, partial success, app reload during Preview,
   app reload after command, owner reconciliation and compensation failure.
9. **Rollback:** disable one flag at a time; derived caches disposable; owner
   state and receipts remain readable; previous Integration version restorable.

## 8. Definition of Ready and Definition of Done

A slice is **Ready** only when its owner approves the boundary, inputs/outputs,
freshness, privacy, failure vocabulary, receipt schema, eval corpus, feature flag
and exact rollback.

A slice is **Done** only when:

- browserless contracts and adapters pass architecture checks;
- every visible fact has owner/source/freshness provenance;
- the real visible Step-17 matrix passes without `element.click()` or DOM state
  mutation shortcuts;
- desktop/mobile/reduced-motion UI uses the accepted bright Living Sheet/map/
  timeline language;
- Integration bytes are committed, immutable, hashed and rollback-addressable;
- no Main, Production, DB/RLS, Secret or Edge Function change occurred.
