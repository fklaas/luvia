# Luvia Affiliate Activation and Hotel Decision Plan

Date: 2026-09-02
Status: **B1 LOCAL LIVE-GATEWAY CANDIDATE — APPLICATIONS/CREDENTIALS NOT YET SUPPLIED — NO PROVIDER CLAIMED ACTIVE**

## 1. Product decision

Luvia will not render one hotel card per portal and will not claim to search
“all portals”. No lawful commercial API guarantees that. Instead, the Hotel
owner uses a provider-neutral offer model and a small number of deliberately
broad supply layers:

1. **Breadth/metasearch:** KAYAK Affiliate Network, after approval, for broad
   hotel/flight/car price discovery and attributed handoff.
2. **Deep hotel supply:** Expedia Rapid and Booking.com Demand only after their
   separate commercial/API qualification; these paths can later support live
   quote, booking, modification, cancellation and provider messaging.
3. **Fast tracked monetization:** Expedia Group Travel Creator and Booking.com
   Affiliate as tracked handoffs while deep API access is unavailable.
4. **Specialist supply:** Hostelworld for hostels and budget accommodation.
5. **Verified direct property path:** official hotel booking URL, verified
   booking email or provider chat fallback when no approved transactional API
   exists.

**Hard product gate:** without a live price response there is no price ranking.
Affiliate links alone permit only a handoff. The UI may still help select a
property by evidenced fit, but it must not show “günstigster”, “Preisvergleich”
or “bester Preis”. With one live source it may rank prices only inside that
named source. “Quellenübergreifend verglichen” requires at least two successful
live-price sources. “Bester Marktpreis” is never claimed.

Affiliate approval and live-price access are separate capabilities. A tracked
link never becomes a live-price API and an external checkout never becomes a
Luvia-confirmed reservation.

## 2. How Luvia helps a person choose a hotel

The product answers two questions separately:

### 2.1 Which property fits this trip?

Luvia evaluates only evidenced fields: exact stay dates and party, destination
and route context, total budget, room/bed/board requirements, location,
amenities, accessibility requirements, profile preferences, cancellation and
payment preferences, current availability/freshness and provider reliability.
It does not infer sensitive needs or fill missing facts with AI prose.

The compact result is three transparent choices, not a hidden universal score:

- **Günstigster vergleichbarer Gesamtpreis:** mandatory taxes, fees and
  at-property charges included for the exact stay and party.
- **Beste flexible Option:** refundable/free-cancellation and payment terms
  first; complete total price breaks ties.
- **Beste persönliche Passung:** explained profile, location, amenity,
  accessibility and reliability evidence; affiliate commission is excluded.

### 2.2 Through which source should this exact offer be booked?

The same property is deduplicated into one user card. Provider offers are
price-compared only inside an equivalent rate group: same property, dates,
party/rooms, currency, room/board/bed signature and complete mandatory charges.
A cheaper non-refundable room is not silently presented as the same product as
a flexible breakfast rate.

The Booking Owner then chooses the safest available route:

`connected quote/API → verified official hotel link → approved tracked handoff → verified hotel email/thread → manual fallback`

The user confirms before leaving Luvia or sending a request. Booking Center
stores the handoff/request, provider identity, quoted terms, correlation and
later status evidence. Unknown outcomes block blind retries.

## 3.1 Separate live hotel-price access ranking

Affiliate ease and Hotel-USP readiness are different rankings.

| Price proof | Strategic USP | Provider | Actual value | Important limit |
|---:|---:|---|---|---|
| 1 | 5 | Amadeus Self-Service Hotels | Fast test account, free quota and quick pay-as-you-go production; real-time hotel offers | One distribution inventory, no hotel images, no dependable affiliate margin, API cancellation unavailable |
| 2 | 4 | HBX Group Hotelbeds | Free evaluation key; final B2B rates and full availability/check-rate/book/manage contract | Production requires profile, commercial terms and certification |
| 3 | 1 | KAYAK Hotels API | Live pricing/availability from hundreds of providers; strongest cross-provider comparison layer | Business/use-case review and production API approval |
| 4 | 2 | Expedia Rapid | Live rates/availability for about 700,000 accommodations, full price breakdown, cancellation and deep booking | Distribution partner contract and launch approval |
| 5 | 3 | Booking.com Demand | Search/total/charges/room policies plus redirect or full order path and eligible third-party rates | Managed Affiliate Partner contract; API is not a mirror of the consumer site |

Therefore the fastest honest sequence is:

1. obtain Amadeus Self-Service and Hotelbeds evaluation credentials to make
   the visible product consume real price-shaped responses immediately;
2. submit KAYAK simultaneously because this is the primary price-comparison
   USP dependency;
3. apply for Expedia Rapid and Booking.com Managed Affiliate access using the
   working Hotel decision surface and early conversion evidence;
4. never delay the KAYAK/Expedia/Booking applications until the prototype is
   “perfect”—their approval latency is external and should run in parallel.

## 4. What the owner must provide for applications

The legal representative—not Codex and not the AI runtime—submits and accepts
the external applications. Prepare once and reuse where permitted:

1. legal company name, address and authorized representative;
2. Luvia domain with HTTPS, working product, imprint, privacy policy and clear
   affiliate disclosure;
3. product description, target markets, supported languages and why the
   integration benefits travelers;
4. current/expected traffic, conversion and booking volumes, with no invented
   numbers;
5. business, technical and customer-support contacts;
6. tax, bank and payout information entered only in the provider portal;
7. provider-specific terms, brand rules, deep-link policy and prohibited
   traffic-channel review.

Credentials are never committed. After approval, only non-secret provider
identity/status/configuration is versioned; API keys, client secrets and
webhook secrets enter the Integration secret store.

## 5. Machine and release boundaries

- `booking.stay-decision.v1` normalizes prices, rejects incomplete/stale bait
  rates, groups equivalent room products, deduplicates hotels and emits the
  three explained choices.
- It emits `fit_only`, `single_source_live_prices` or
  `cross_source_live_prices`. These modes are derived from successful live
  price sources, never from affiliate-link availability.
- `booking.affiliate-activation.v1` stores the evidence-ranked activation order,
  application states and checklist without pretending an application exists.
- All prepared provider profiles remain `partner_required`, `discovery` or
  fail-closed until contract, credentials, health and positive Integration E2E.
- Monetization signals cannot raise a hotel/offer in the user ranking.
- Coverage explicitly names attempted, successful and failed sources and says
  `CONNECTED_AUTHORIZED_SOURCES_ONLY`; no all-market best-price guarantee.
- Activation proceeds one provider at a time through Owner Contract, Edge
  adapter, health, quote/handoff, correlation/readback, failure tests, visible
  Step 17, commit, immutable Integration release, byte proof and rollback.

## 7. Current acceptance evidence

Local automated evidence currently proves:

- one hotel card can contain two provider offers;
- only equivalent room-rate signatures become direct provider-price groups;
- incomplete mandatory charges and stale quotes are excluded;
- cheapest and flexible outcomes may intentionally differ;
- arbitrary affiliate commission input cannot influence the result;
- failed provider coverage stays visible;
- no all-market guarantee is emitted;
- external applications and credentials remain owner/secret-store actions.

The implementation additionally proves:

- the authenticated `booking-hotel-offer-search` gateway calls only providers
  whose capability, connection and activation rows are ready;
- Amadeus OAuth/Hotel Offers and Hotelbeds signature/Hotel Availability are
  represented by separate fail-closed Edge adapters with no committed secret;
- only `source=provider_api` and `live=true` envelopes may contribute a price;
- child occupancy, missing provider destinations, incomplete mandatory totals,
  stale quotes and unavailable partners fail closed;
- `booking.stay.search` is a typed semantic Chat read through
  `booking.v1.reads.searchStayOffers`, not a keyword-triggered shadow path;
- the visible default and 390×844 fixture proves one Hotel card, two comparable
  controlled tariffs, `TT.MM.JJJJ`, no horizontal overflow, a no-source
  `fit_only` state and zero browser warning/error.

This is not yet a public live hotel-price acceptance. The visible consumer is
locally accepted, but a real approved provider, credentials, public Integration
operation, immutable bytes and exact release rollback remain open B1 work.
