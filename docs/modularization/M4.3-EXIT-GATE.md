## Ziel

M4.3 schafft die kontrollierte technische Grundlage, damit zukünftige parallele Luvia-Streams unfertige oder gestaffelt ausrollbare Änderungen sicher hinter Feature Flags entwickeln können und dabei auf einer wiederholbaren, kontrollierten Regression-Baseline arbeiten.

M4.3 darf dabei insbesondere **keine zweite Domain-, Capability-, Permission-, Module- oder Konfigurationswahrheit** erzeugen.

Das Exit Gate verlangt deshalb:

- eine moderne zentrale Feature-Flag-Registry im Platform-Layer,
- klar begrenztes Flag-Schema,
- fail-closed Verhalten,
- keine frei mutierbare parallele Runtime-Wahrheit,
- keine Reaktivierung des historischen Feature-Flag-Systems,
- eindeutige Ownership,
- definierte Feature-Flag-Governance,
- verbindliche Merge-Reihenfolge,
- kontrollierten Regression-Harness,
- Evergreen-Ersatz für weiterhin gültige historische Invarianten,
- Release-Konsistenz,
- Erhalt aller M3 Contract Adapter,
- Erhalt der M4.2 Ownership-/DB-Guardrails.

## 3. Feature-Flag Owner Contract

Zulässige Owner-Präfixe:

~~~text
platform
trip
places
booking
media
identity
intelligence
consumer

~~~

Flag-ID-Konvention:

~~~text
<owner>.<feature>
~~~

Beispiele:

~~~text
booking.parallel-proof
consumer.preview-surface
platform.integration-proof
social.foundation-preview
~~~

Die Registry erzwingt:

- gültigen Owner;
- lowercase dotted Flag-ID;
- Owner-Präfix muss mit `owner` übereinstimmen;
- konfliktfreie identische Registrierung ist idempotent;
- widersprüchliche Wiederregistrierung wird abgelehnt.

## 4. Geschlossenes Definition-Schema

M4.3 verhindert, dass Feature Flags zu einem versteckten generischen Konfigurationscontainer werden.

Persistierte Flag-Definitionen enthalten ausschließlich:

~~~text
version
id
owner
description
defaultEnabled
temporary
~~~

Die Registry übernimmt keine beliebigen Properties aus der Eingabedefinition.

Expliziter Härtungsnachweis:

Testinput enthält kontrolliert:

~~~text
version:'evil'
secretConfig:'must-not-survive'
~~~

Erwartetes Verhalten:

~~~text
bookingFlag.version === '1.0.0'
secretConfig is absent
~~~

Testresultat:

~~~text
M4.3 Feature Flag Registry: OK
~~~

Damit ist verhindert, dass über Flag-Definitionen eine verdeckte zweite Konfigurationswahrheit aufgebaut wird.

---

## 5. Fail-Closed / Runtime-Mutation-Gate

Unbekannte Flags evaluieren auf:

~~~text
known: false
enabled: false
owner: null
source: unknown
~~~

Damit gilt:

~~~text
UNKNOWN FLAG = DISABLED
~~~

Die M4.3 Foundation stellt bewusst keine frei mutierenden Runtime-APIs bereit wie:

~~~text
enable()
disable()
setEnabled()
override()
activate()
mount()
~~~

Feature Flags sind damit in M4.3 kontrollierte Rollout-Gates und kein dynamischer zweiter Runtime-State-Store.

## 18. Feature-Flag Governance

Normative Quelle:

`docs/modularization/PARALLEL-DEVELOPMENT-RULES.md`

M4.3 ergänzt dort verbindlich:

- Flags sind temporäre Rollout-Gates;
- Registry-Mechanik ist Platform-owned;
- Owner-Präfix ist verpflichtend;
- unbekannte Flags fail closed;
- unvollständige Funktion muss mit deaktiviertem Flag sicher bleiben;
- Flags ersetzen keine Auth-/Privacy-/Permission-/Capability-/Module-/Domain-Truth;
- beliebige versteckte Definitionseigenschaften sind verboten;
- keine parallele Flag-Wahrheit via `localStorage`, Query Parameter, ad-hoc Globals oder verstecktes JSON;
- historischer Feature-Flag-Pfad darf nicht reaktiviert werden;
- keine Runtime-Mutations-API in M4.3;
- `defaultEnabled:true` verlangt grüne Tests;
- vollständig ausgerollte Flags müssen später mitsamt totem Gate-Code entfernt werden.

## 19. Merge Order Gate

Normative Quelle:

`docs/modularization/PARALLEL-DEVELOPMENT-RULES.md`

Standardweg:

~~~text
feature/*
  ->
integration
  ->
controlled regression + integration smoke
  ->
main
  ->
production
~~~

Cross-cutting Reihenfolge:

1. Platform-/Contract-/PCR-Änderung zuerst;
2. betroffene Streams synchronisieren gegen den neuen Shared Contract;
3. Domain Owner implementiert Business-Verhalten;
4. Consumer/Social Composition folgt auf stabile Domain-Grenzen;
5. Feature Stream geht über `integration`;
6. Regression und Integration Smoke müssen PASS sein;
7. erst danach Promotion zu `main`;
8. nach Main-Release synchronisieren aktive Streams wieder mit `main`.

Direktes Umgehen von `integration` ist kein Standard-Mergeweg.
