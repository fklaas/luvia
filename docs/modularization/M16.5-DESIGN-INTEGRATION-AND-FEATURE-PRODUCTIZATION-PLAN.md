# M16.5 Design Integration and Feature Productization Plan

Date: 2026-08-26

Status: BINDING EXECUTION PLAN / INTEGRATION ONLY

## 1. Objective and authority

This plan turns the accepted M16.5 design into the productive Luvia product
without weakening the established Core architecture. It is subordinate to the
Master Roadmap, the M16.5 Design/Acceptance Contract and the binding
Profile/Trip onboarding split. If a conflict is found, those higher-order
contracts win and this plan must be corrected before implementation continues.

The target is not a visually new shell containing incomplete or legacy feature
flows. The target is a sequence of owner-backed, end-to-end product slices in
which the accepted design, real functionality, recovery behavior and public
evidence reach parity together.

Main and Production remain locked until the complete M16.5 parity matrix and
the user's explicit Design Freeze are complete. Every intermediate release is a
new immutable Integration version with a documented rollback target.

## 2. Non-negotiable delivery rules

1. Work vertically through complete user outcomes. Do not distribute shallow
   visual fragments horizontally across every Core.
2. Preserve one canonical owner for every Domain Truth. Consumer composes;
   Experience supplies shared interaction semantics; neither becomes a second
   Trip, Places, Booking, Media, Memory or Identity owner.
3. Reuse public owner reads, commands, events and receipts. A redesign does not
   authorize direct private stores, duplicate persistence or a second login.
4. The accepted M16.5 reference is the endpoint. No simplification, legacy
   substitution or alternative visual interpretation can close a parity row.
5. The accepted Living Compass interaction is frozen after M16.5Q. It may be
   changed only to correct a reproduced regression with a dedicated test; it is
   not reopened during feature productization.
6. A feature is not accepted because its destination renders. The complete
   sequence must preserve selection, scroll, focus, filters, map state, Back,
   reload, responsive behavior, Reduced Motion, loading, empty, error, offline
   and recovery behavior as applicable.
7. No functional acceptance is granted without a real visible E2E sequence.
   Synthetic contract tests and DOM assertions are necessary but insufficient.
8. A slice changes Integration only. Main and Production require the separate
   complete Design Freeze decision.

## 3. Status vocabulary

The Product Surface Matrix uses only these ordered states:

- `NOT CONNECTED`: accepted reference exists, but the productive route does not
  reach an owner-backed implementation.
- `SHELL-WIRED`: productive navigation reaches a surface, but functional and/or
  visual parity is materially incomplete.
- `VISUAL PARITY`: the accepted desktop/mobile/motion/state design is present,
  but owner-backed functional acceptance is not complete.
- `FUNCTIONAL PARITY`: the intended owner-backed outcomes and continuity rules
  pass focused tests; broader resilience or public evidence is still open.
- `RESILIENCE COMPLETE`: Back, reload, offline/reconnect, stale async work,
  accessibility, responsive and Reduced Motion gates applicable to the surface
  pass locally.
- `PUBLIC VERIFIED`: a newly versioned immutable Integration build passes real
  visible stable-origin E2E and source/stable/immutable asset provenance.
- `USER ACCEPTED`: the user has explicitly accepted the complete relevant
  surface on the real target device/browser. This is never inferred from
  automation.

Status is monotonic only while its evidence remains valid. A reproduced defect
immediately reopens the affected row without rewriting prior evidence.

## 4. Vertical slice lifecycle

Every productization slice follows this same closed loop:

1. **Scope lock:** select one user outcome, its reference frames, owner
   contracts, explicitly excluded truth and rollback boundary.
2. **Baseline:** reproduce the current productive behavior with real input and
   retain failing evidence before mutation.
3. **Contract gate:** prove that all reads and mutations cross public owner
   contracts and that Consumer owns presentation state only.
4. **Implementation:** compose the accepted design with the real owner-backed
   behavior; do not introduce a parallel facade or mock truth.
5. **Focused verification:** test normal, loading, empty, error, focus,
   selection, scroll, map/media state, keyboard, touch, responsive and Reduced
   Motion behavior applicable to the slice.
6. **Recovery verification:** test Back, reload, rapid newer intent, stale async
   completion, session exit and offline/reconnect behavior applicable to the
   slice.
7. **Regression:** run the focused guard, architecture/ownership gates, Safe
   Regression, NFR-0 and the visual-inventory freshness gate.
8. **Integration release:** publish only a coherent new immutable Integration
   version, prove exact assets and run real visible E2E on the stable origin.
9. **Acceptance record:** record what is visible, what remains open, tests,
   commit/version/deployment/URLs and exact rollback. User acceptance remains a
   separate explicit event.

## 5. Ordered execution corridor

### Gate 0 — M16.5Q closure

App 13.82.64 has passed the local/public matrices and the user's subsequent
physical-handset retest. This closes the Compass recovery slice, not the full
M16.5 Design Freeze. Compass behavior is now frozen as shared navigation
infrastructure.

### Gate 1 — Places continuity correction

First reproduce and fix the concrete open defect: opening `Details & Evidenz`
for a later horizontally scrolled result can return the result rail to its
beginning while showing the later result's detail. The selected Place, exact
rail position, map marker/viewport, filters, query, focus origin and close/Back
return must remain one coherent state. This is a bounded correction to the
existing Places product slice, not a claim that the whole Places Experience is
complete.

### Gate 2 — Public Landing and real Authentication

Replace the productive public entry with the accepted cinematic landing design
while retaining the existing real Supabase/Auth session owner. The slice covers
signed-out landing, login, registration entry, pending, success, invalid/expired
link, error, retry, restored session and signed-in handoff. It must not add a
second identity store, a fake login or a visual-only authentication path.

### Gate 3 — Identity/Profile onboarding

Implement the accepted Profile onboarding as its own owner-backed flow:
identity, consent and the global Reisekompass belong to Identity. Completion,
skip/resume, validation, session exit, reload and editing an existing profile
must be explicit. No Trip is created by this flow.

### Gate 4 — First-Trip Composer

Implement the separate accepted Trip onboarding against Trip-owned commands and
receipts. Creation, participants, dates, destination, validation, draft/resume,
idempotency, confirmation, active-Trip activation and failure recovery belong
to this slice. Profile completion is an input, not copied Trip truth.

### Gate 5 — Places Golden Slice

After continuity is stable, audit Places end to end: discovery, search,
categories, filters, map/list synchronization, detail/evidence, favorite/save,
planning handoff, empty/error/offline states, Back/reload and large result sets.
M16.5N/O proves architecture and the first productive spatial composition; it
does not by itself prove exhaustive Places Experience parity.

### Gates 6–8 — Existing owner-backed product areas

Proceed in this order:

1. Booking discovery, provider evidence, selection, external handoff,
   reservation/status/recovery and Trip/Journey projection.
2. Today and Journey/Trip day composition, including conflict and provenance
   behavior without moving Journey truth into Places.
3. Media acquisition and Memory/Memories composition, including the accepted
   distinct capture versus gallery routes, lifecycle and recovery.

Each remains a separate rollback-capable Integration release unless two changes
are inseparable parts of the same user outcome and share the same owner/risk
boundary.

### Gate 9 — Remaining surfaces and complete Design Freeze

Complete Profile/Settings, Collaboration, Attention/Inbox, Wallet placeholders
only where owner-backed, and every overlay/deep-link/recovery row in the Product
Surface Matrix. Admin and Social remain explicitly reserved, not simulated.
Only after every required row reaches `USER ACCEPTED` or an explicitly approved
deferred state may the user grant the M16.5 Design Freeze and authorize a
separate Main/Production promotion decision.

### Gate 10 — New Core evolution

M18 owner-first Core work begins after Design Freeze in the Roadmap order:
Collaboration, Attention, Travel Wallet, Reviews, Admin, Social, Universal
Search and Intelligence Evolution II. Their future UI must consume the same
Experience language and public contracts; none is pulled forward as a mock
inside M16.5.

## 6. Definition of Done for one surface

A surface can reach `USER ACCEPTED` only when all applicable items are true:

- accepted visual and motion reference matched on desktop and real mobile;
- mouse, real touch and keyboard operation preserve exact intent;
- owner-backed reads and commands pass with receipts where mutations occur;
- loading, empty, error, permission, offline and stale-result behavior is
  honest and recoverable;
- selection, scroll, focus, filters, map/media position and open detail survive
  all transitions where the product contract requires continuity;
- Back, Forward, deep link and reload are deterministic;
- Reduced Motion and accessibility semantics pass without hidden focused
  descendants or moving hit targets;
- no console warning/error attributable to the application sequence;
- focused tests, Safe Regression, ownership/contract gates, NFR-0 and visual
  inventory are green;
- source, stable and immutable Integration assets are proven exact;
- real visible public E2E is retained; and
- the user explicitly accepts the relevant complete surface.
