## 1. Decision

Date: 2026-08-26

Status: BINDING BASELINE / INTEGRATION IMPLEMENTED / BOUNDED PUBLIC EVIDENCE PASS

Channel: Integration only

M16.5S implements Gate 2 of the binding M16.5 Design Integration and Feature
Productization Plan. The accepted public Landing composition is adopted as the
one-to-one visual and motion target. The existing Supabase Auth session remains
the only authentication owner. This scope does not authorize Main or
Production. The delivered Integration result grants only the bounded
Landing/Auth evidence recorded below; it grants no complete M16.5 visual or
functional acceptance.

The Landing and Authentication rows are one user-outcome release. A decorative
Landing without real login, registration, recovery and session restoration is
not releasable. A working legacy login inside a simplified or substituted
Landing is also not releasable.

Profile/Trip onboarding is not folded into account access: Profile onboarding
starts at Gate 3 and First-Trip creation remains Gate 4.

### 3.1 Delivered Integration outcome

App 13.82.72 / Core 4.82.72 now mounts the complete accepted public Landing as
the productive signed-out surface and keeps the existing Supabase Auth owner as
the only login, registration, OAuth, recovery and session authority.

The first account action is intentionally no longer a form. The bright,
softly-masked travel opening leads through the editorial journey to a large
Living Compass threshold. A deliberate Compass click reveals two signposted
paths: “Weiterreisen” and “Meine Reise beginnen”. Only those paths open the

Compass guide explains email confirmation and previews the later Ernährung,

truth. Persisted Profile/preferences onboarding remains Gate 3 and First-Trip
onboarding remains Gate 4.

The public product theatre uses the deployable
`app/demo/living-compass-browser.html` document. The earlier excluded
`tests/fixtures/**` reference caused public SPA fallback recursion and broken
relative script paths; it is no longer part of the productive Landing. The
deployable document has root-relative base ownership, `noindex,nofollow` and
explicit Service Worker cache coverage.

## 4. Ownership and composition

| Concern | Owner | Allowed M16.5S responsibility |
| --- | --- | --- |
| Public Landing structure and responsive composition | Consumer | Mount accepted sections, route public actions and preserve signed-out reachability |
| Tokens, motion, Living Compass thread, Reduced Motion | Experience | Project the accepted contract without new Domain Truth |
| Supabase session, password/OAuth auth, recovery commands | Identity/Auth | Remain the sole authentication authority |
| Session activation/deactivation and route handoff | Platform/App Shell | Orchestrate owner events, history, cleanup and boot recovery |
| Profile data and onboarding | Identity/Profile | Receive a confirmed authenticated account in Gate 3; not absorbed into Landing |
| First Trip creation | Trip | Remains Gate 4; no Trip truth is created by the Landing |

Forbidden shortcuts:

- no second auth/session store and no direct Supabase call from Landing UI;
- no fake login, demo credential or visual-only success state;
- no recreation of the accepted Landing as a smaller hero-only screen;
- no automatic profile preference or Trip mutation during account creation;
- no iframe substitution for the productive signed-out root;
- no private Trip, Places, Memory or Booking truth in the public Landing;
- no Main/Production promotion before the complete M16.5 Design Freeze.

## 5. Mandatory state matrix

| State | Visible requirement | Owner result |
| --- | --- | --- |
| `BOOT_LOADING` | Stable branded start without a blank/legacy flash | App Shell awaits Auth exactly once |
| `LANDING_READY` | Complete accepted Landing and functional public navigation | No private account or Trip data |
| `LOGIN_IDLE` | Accepted login surface reachable from all account CTAs | Existing Auth UI/commands mounted in the accepted composition |
| `LOGIN_INVALID` | Inline field-level validation, focus retained | No network call |
| `LOGIN_PENDING` | One disabled submit and visible progress | One `signInWithPassword` request |
| `LOGIN_ERROR` | Safe localized error and retry | No false session activation |
| `LOGIN_SUCCESS` | Intentional transition into restored account state | Session event drives App Shell; UI does not forge success |
| `REGISTER_IDLE` | Minimal account fields and clear confirmation expectation | Profile/travel preference collection deferred to Gate 3 |
| `REGISTER_PENDING` | One disabled submit and progress | One Auth owner request |
| `REGISTER_CONFIRM_EMAIL` | Persistent confirmation instructions and login return | No authenticated claim before Auth owner confirms it |
| `REGISTER_ERROR` | Localized retryable/non-retryable message | Entered non-secret fields retained where safe |
| `RECOVERY_REQUEST_IDLE` | Email entry reachable from login | No password prompt |
| `RECOVERY_REQUEST_PENDING` | One request and visible progress | Auth owner sends configured recovery link |
| `RECOVERY_REQUEST_SENT` | Non-enumerating success guidance | No account existence disclosure |
| `RECOVERY_CALLBACK_VALID` | New/repeat password surface | Auth owner updates the active recovery session |
| `RECOVERY_CALLBACK_INVALID` | Expired/invalid-link explanation and resend path | No password mutation |
| `OAUTH_PENDING` | Provider and redirect progress visible | Existing `signInWithOAuth` boundary |
| `OAUTH_ERROR` | Provider failure returns to usable login | No dead or blank page |
| `SESSION_RESTORE` | Branded bounded wait, then exact signed-in destination | Existing session is refreshed, not recreated |
| `SESSION_EXPIRED` | Safe return to Landing/login with reason | All signed-in hosts and overlays unmount |
| `SIGNOUT_RETURN` | Public Landing reappears without old user data/flash | Local session exit and owner cleanup complete |
| `INVITE_PENDING` | Existing invite flow may own signed-out view | Landing remains fallback if invite mount fails |
| `OFFLINE_OR_TIMEOUT` | Retryable Landing/Auth state; no infinite spinner | No false success and no destructive cache reset |

## 6. Implemented slices and retained boundary

1. Adopt the pinned Landing DOM, assets, CSS and motion as a productive
   Consumer/Experience composition with no auth mutation.
2. Replace prototype CTA destinations with accessible in-composition actions
   that open the real Auth owner surface while preserving accepted geometry and
   motion.
3. Separate minimal account registration from Profile/Trip onboarding and bind
   login/register pending, error and confirmation states.
4. Implement the missing recovery callback/update-password surface through the
   existing Auth owner.
5. Bind OAuth return, session restoration, expiry, logout and invite precedence
   through App Shell lifecycle cleanup.
6. Verify desktop, responsive mobile, keyboard, reload, Back, Reduced Motion,
   offline/timeout and no-blank/no-flash behavior before any public release;
   retain physical-device touch as a separately evidenced gate where the test
   environment cannot dispatch hardware touch.

These slices were delivered as one cohesive Landing/Auth user outcome on
Integration. Intermediate commits exist, but rejected or partial public
candidates are not labelled accepted.

- deterministic Auth-owner fixture for every mandatory state above;
- no secret, password or token in DOM diagnostics, URL, storage assertions or

- local real Edge desktop/mobile/keyboard/touch/reload/Back/Reduced Motion E2E;

No functional acceptance is granted without the real visible E2E sequence.
Main and Production remain unchanged.
